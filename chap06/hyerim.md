# 6장 타입스크립트 컴파일

## 6.1 자바스크립트의 런타임과 타입스크립트의 컴파일

### 런타임과 컴파일타임

- **컴파일타임**은 소스코드가 컴파일러에 의해 실행 가능한 코드로 변환되는 과정이다.
- **런타임**은 컴파일을 마친 프로그램이 메모리에 적재되어 실제로 실행되는 과정이다.
- 타입스크립트의 타입 검사는 컴파일타임에 수행되며, 타입 정보는 자바스크립트로 변환되는 과정에서 제거된다.

### 자바스크립트 런타임

- 자바스크립트 런타임은 자바스크립트 코드가 실행되는 환경을 말한다.
- 대표적인 자바스크립트 런타임으로 웹 브라우저와 Node.js가 있다.
- 브라우저 런타임은 자바스크립트 엔진뿐만 아니라 웹 API, 콜백 큐, 이벤트 루프, 렌더링 관련 구성 요소 등을 포함한다.
- Node.js도 자바스크립트 엔진과 이벤트 루프를 제공하지만, 브라우저의 웹 API 대신 파일 시스템이나 네트워크처럼 서버 환경에 필요한 API를 제공한다.

### 타입스크립트의 컴파일

- 타입스크립트 코드는 타입스크립트 컴파일러인 `tsc`를 통해 자바스크립트 코드로 변환된다.
- 고수준 언어인 타입스크립트를 또 다른 고수준 언어인 자바스크립트로 변환하므로 이 과정을 **트랜스파일**이라고도 한다.
- 같은 수준의 언어 사이에서 코드를 변환한다는 의미에서 타입스크립트 컴파일러를 **소스 대 소스 컴파일러**라고 부르기도 한다.

타입스크립트 코드가 실행되기까지의 과정은 다음과 같다.

1. `tsc`가 타입스크립트 소스코드를 타입스크립트 AST로 만든다.
2. 타입 검사기가 AST를 확인하여 타입을 검사한다.
3. 타입스크립트 AST를 자바스크립트 소스코드로 변환한다.
4. 자바스크립트 런타임이 자바스크립트 소스코드를 다시 AST로 만든다.
5. 자바스크립트 엔진이 AST를 바이트 코드 또는 기계어로 변환한다.
6. 런타임이 변환된 코드를 평가하여 프로그램을 실행한다.

- 타입스크립트의 타입 정보는 주로 1~2단계에서 사용되고, 자바스크립트 코드가 생성될 때 제거된다.
- 따라서 런타임에는 타입스크립트의 타입이 존재하지 않으며, 타입 자체를 런타임 값처럼 사용할 수 없다.

```ts
const name: string = "woowa";
const age: number = 12;
```

위 코드를 자바스크립트로 변환하면 타입 표기가 사라진다.

```js
const name = "woowa";
const age = 12;
```

## 6.2 타입스크립트 컴파일러의 동작

### 코드 검사기로서의 타입스크립트 컴파일러

- 타입스크립트 컴파일러는 프로그램을 실행하기 전에 코드를 정적으로 분석하여 타입 오류를 찾아낸다.
- 자바스크립트에서는 실행해야 발견할 수 있는 오류 중 일부를 컴파일타임에 미리 확인할 수 있다.

```ts
const developer = {
  work() {
    console.log("working");
  },
};

developer.sleep();
// Property 'sleep' does not exist on type '{ work(): void; }'.
```

- 다만 타입 검사는 실제 런타임 값을 모두 보장하지 않는다.
- API 응답이나 사용자 입력처럼 런타임에 결정되는 값이 선언된 타입과 다르면, 타입 검사에 통과했더라도 런타임 오류가 발생할 수 있다.

### 코드 변환기로서의 타입스크립트 컴파일러

- 타입스크립트 컴파일러는 타입스크립트 문법과 타입 정보를 제거하여 자바스크립트 코드로 변환한다.
- `tsconfig.json`의 `target` 옵션에 따라 최신 자바스크립트 문법을 구버전 문법으로 변환할 수도 있다.

```ts
const welcome = (name: string) => {
  console.log(`Hi, ${name}`);
};
```

`target`을 `ES5`로 설정하면 다음과 비슷한 코드가 생성된다.

```js
var welcome = function (name) {
  console.log("Hi, ".concat(name));
};
```

### 타입 검사와 코드 변환의 독립성

- 타입 검사와 타입스크립트 코드를 자바스크립트로 변환하는 작업은 서로 독립적이다.
- 기본적으로 타입 오류가 있어도 자바스크립트 파일은 생성될 수 있다. 타입 오류가 자바스크립트 코드의 실행을 자동으로 막는 것은 아니다.
- 타입 오류가 있을 때 결과 파일을 생성하지 않으려면 `tsconfig.json`에서 `noEmitOnError` 옵션을 `true`로 설정해야 한다.

```json
{
  "compilerOptions": {
    "noEmitOnError": true
  }
}
```

```ts
const age: number = "twelve";
// 타입 오류가 발생하지만 noEmitOnError가 false라면 JS가 생성될 수 있다.
```

- 생성된 자바스크립트에는 타입 정보가 없으므로, 코드가 실행된 뒤 발생하는 문제는 자바스크립트 런타임에서 처리된다.
- 즉 타입스크립트의 타입 오류가 런타임에 타입 검사로 다시 처리되는 것이 아니라, 변환된 자바스크립트의 실제 동작에 따라 런타임 오류가 발생할 수 있다.

## 6.3 타입스크립트 컴파일러의 구조

타입스크립트 컴파일러는 다음 과정을 거쳐 소스코드를 분석하고 결과 파일을 생성한다.

```text
tsconfig.json
      ↓
프로그램 → 스캐너 → 파서 → 바인더 → 체커 → 이미터
           토큰      AST      심볼     타입 검사   결과 파일
```

### 프로그램(Program)

- `tsc` 명령어를 실행하면 프로그램 객체가 컴파일 과정을 시작한다.
- 프로그램은 `tsconfig.json`에 명시된 컴파일 옵션과 대상 파일을 읽는다.
- 진입 파일과 `import` 관계를 따라가며 컴파일에 필요한 소스 파일 전체를 관리한다.

### 스캐너(Scanner)

- 스캐너는 소스코드를 읽고 **어휘 분석**을 수행한다.
- 소스코드를 의미 있는 최소 단위인 **토큰**으로 나눈다.

```ts
const language = "TypeScript";
```

위 코드는 `const`, `language`, `=`, `"TypeScript"`, `;` 등의 토큰으로 분리된다.

### 파서(Parser)

- 파서는 스캐너가 만든 토큰을 구문적으로 분석하여 **AST(추상 구문 트리)**를 만든다.
- AST는 소스코드의 문법 구조를 트리 형태로 나타낸 자료구조다.
- 최상위에는 소스 파일을 나타내는 `SourceFile` 노드가 있고, 그 아래에 변수 선언이나 함수 선언 등의 노드가 연결된다.

```text
SourceFile
└─ VariableStatement
   └─ VariableDeclaration
      ├─ Identifier(language)
      └─ StringLiteral("TypeScript")
```

### 바인더(Binder)

- 바인더는 AST를 탐색하면서 선언에 대응하는 **심볼**을 생성한다.
- 심볼은 변수, 함수, 클래스, 인터페이스 등 코드에서 선언된 대상의 정보를 나타낸다.
- 각 선언과 심볼을 연결하고 스코프별 심볼 테이블을 구성하여, 같은 이름이 무엇을 가리키는지 알 수 있게 한다.

### 체커(Checker)

- 체커는 AST를 탐색하면서 바인더가 만든 심볼 정보를 활용해 타입 검사를 수행한다.
- 값이 선언된 타입에 할당될 수 있는지, 존재하지 않는 프로퍼티에 접근하는지 등을 검사한다.
- 발견한 오류는 진단 정보로 수집하여 개발자에게 보여준다.

### 이미터(Emitter)

- 이미터는 AST를 바탕으로 자바스크립트 등의 결과 파일을 생성한다.
- 컴파일 옵션에 따라 다음과 같은 파일을 만들 수 있다.
  - `.js`: 실행할 자바스크립트 파일
  - `.d.ts`: 타입 선언 파일
  - `.js.map`: 원본 타입스크립트와 생성된 자바스크립트를 연결하는 소스맵
- 타입 오류가 있더라도 `noEmitOnError`가 활성화되어 있지 않으면 이미터가 결과 파일을 생성할 수 있다.

### 전체 흐름 정리

1. 프로그램이 컴파일 옵션과 대상 파일을 결정한다.
2. 스캐너가 소스코드를 토큰으로 분리한다.
3. 파서가 토큰을 분석하여 AST를 만든다.
4. 바인더가 선언과 심볼을 연결한다.
5. 체커가 AST와 심볼을 바탕으로 타입을 검사한다.
6. 이미터가 타입 정보를 제거하고 결과 파일을 생성한다.
