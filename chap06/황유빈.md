## 자바스크립트의 런타임과 타입스크립트의 컴파일

### 런타임과 컴파일타임

- **컴파일타임**: 소스코드가 기계가 실행할 수 있는 코드로 변환되는 과정. 사람이 쓴 고수준 언어를 저수준 언어로 바꾼다.
- **런타임**: 변환된 코드가 메모리에 올라가 실제로 실행되는 시점.

### 자바스크립트 런타임

자바스크립트가 실행되는 환경을 말한다. 대표적으로 크롬·사파리 같은 브라우저와 Node.js 가 있다. 런타임은 자바스크립트 엔진(V8 등), 웹 API(브라우저 기준), 콜백 큐, 이벤트 루프 등으로 구성된다.

런타임에서 생기는 에러의 예시는 다음과 같다. 문법은 맞지만 실행해 봐야 터진다.

```js
let foo = 7;
foo(); // TypeError: foo is not a function

const testArr = null;
if (testArr.length !== 0) {
  console.log("hi");
} // TypeError: Cannot read properties of null (reading 'length')
```

### 타입스크립트의 컴파일

`tsc` 는 타입스크립트 코드를 자바스크립트 코드로 바꾼다. 고수준 언어를 같은 수준의 다른 언어로 바꾸는 것이라 **트랜스파일(source-to-source compile)** 이라고 부르기도 한다.

타입스크립트 코드가 실행되기까지의 과정은 다음과 같다.

1. 타입스크립트 소스코드를 타입스크립트 AST 로 만든다. (`tsc`)
2. 타입 검사기가 AST 를 확인해 타입을 검사한다. (`tsc`)
3. 타입스크립트 AST 를 자바스크립트 소스코드로 변환한다. (`tsc`)
4. 자바스크립트 소스코드를 자바스크립트 AST 로 만든다. (런타임)
5. AST 가 바이트 코드로 변환된다. (런타임)
6. 런타임에서 바이트 코드가 평가되어 프로그램이 실행된다. (런타임)

> **AST(추상 구문 트리)**: 소스코드에서 공백·주석 같은 불필요한 요소를 빼고, 구문을 트리 형태로 나타낸 자료구조. 트리의 각 요소를 **노드** 라고 한다.

핵심은 **타입 검사가 1~3 단계, 즉 컴파일타임에서만 일어난다** 는 점이다. 3 단계에서 타입 정보는 모두 지워지므로 런타임에는 타입이 존재하지 않는다. 그래서 타입스크립트를 **정적 타입 검사기** 라고 부른다.

```ts
const name: string = "zig";
const age: number = 20;
```

```js
const name = "zig";
const age = 20;
```

## 타입스크립트 컴파일러의 동작

### 코드 검사기로서의 타입스크립트 컴파일러

타입스크립트 컴파일러는 코드를 실행하기 전에 타입 오류를 찾아낸다.

```js
const developer = {
  work() {
    console.log("working...");
  },
};

developer.work(); // working...
developer.sleep(); // TypeError: developer.sleep is not a function
```

자바스크립트에서는 `sleep` 이 없다는 걸 실행해 봐야 안다. 같은 코드를 타입스크립트로 쓰면 컴파일타임에 바로 잡힌다.

```ts
developer.sleep(); // Property 'sleep' does not exist on type '{ work(): void; }'
```

다만 타입스크립트가 잡는 건 **정적으로 분석할 수 있는** 오류뿐이다. 서버에서 받은 데이터처럼 런타임에야 실제 값이 정해지는 경우는 선언된 타입을 그대로 믿기 때문에, 실제 응답이 타입과 다르면 런타임 에러는 그대로 일어난다.

### 코드 변환기로서의 타입스크립트 컴파일러

타입스크립트 컴파일러는 타입을 검사한 뒤 타입 정보를 지우고, `tsconfig` 의 `target` 에 맞춰 구버전 자바스크립트로 변환한다.

```ts
type Fruit = "banana" | "watermelon" | "orange" | "apple" | "kiwi" | "mango";

const fruitBox: Fruit[] = ["banana", "apple", "mango"];

const welcome = (name: string) => {
  console.log(`hi! ${name} :)`);
};
```

`target: "ES5"` 로 컴파일하면 다음과 같다. 타입 선언은 사라지고 화살표 함수·템플릿 리터럴·`const` 도 ES5 문법으로 바뀐다.

```js
"use strict";
var fruitBox = ["banana", "apple", "mango"];
var welcome = function (name) {
  console.log("hi! ".concat(name, " :)"));
};
```

#### 타입 검사와 코드 변환은 독립적이다

타입 오류가 있어도 컴파일러는 자바스크립트 코드를 만들어 낸다. 두 동작이 서로 독립적이기 때문이다.

```ts
const name: string = "zig";
const age: number = "zig"; // Type 'string' is not assignable to type 'number'
```

```js
const name = "zig";
const age = "zig";
```

오류가 있을 때 결과물을 만들지 않으려면 `tsconfig` 의 `noEmitOnError` 옵션을 켠다.

#### 런타임에는 타입을 쓸 수 없다

타입 정보가 지워지므로 런타임 코드에서 타입을 값처럼 사용할 수 없다.

```ts
interface Square {
  width: number;
}

interface Rectangle extends Square {
  height: number;
}

type Shape = Square | Rectangle;

function calculateArea(shape: Shape) {
  if (shape instanceof Rectangle) {
    // 'Rectangle' only refers to a type, but is being used as a value here
    return shape.width * shape.height;
  } else {
    return shape.width * shape.width;
  }
}
```

`instanceof` 는 런타임 연산자인데 `Rectangle` 은 타입이라 컴파일 후에는 존재하지 않는다. 4장에서 본 것처럼 판별자 속성을 두고 **식별할 수 있는 유니온** 으로 좁히면 런타임에도 타입을 구분할 수 있다.

```ts
interface Square {
  kind: "square";
  width: number;
}

interface Rectangle {
  kind: "rectangle";
  width: number;
  height: number;
}

type Shape = Square | Rectangle;

function calculateArea(shape: Shape) {
  if (shape.kind === "rectangle") {
    return shape.width * shape.height;
  } else {
    return shape.width * shape.width;
  }
}
```

#### tsc 와 바벨

바벨도 타입스크립트를 자바스크립트로 바꿀 수 있지만, 타입 정보를 **지우기만** 하고 타입 검사는 하지 않는다. 그래서 바벨로 빌드하는 프로젝트는 타입 검사를 `tsc --noEmit` 으로 따로 돌린다.

## 타입스크립트 컴파일러의 구조

타입스크립트 컴파일러는 다음 다섯 단계로 동작한다.

```
tsconfig.json → 프로그램 → 스캐너 → 파서 → 바인더 → 체커 → 이미터
                          (토큰)   (AST)   (심볼)   (타입 검사) (JS 출력)
```

### 프로그램

`tsc` 명령어로 실행되면 먼저 `tsconfig.json` 을 읽어 컴파일 옵션과 컴파일할 파일 목록을 정한다. 시작 파일부터 `import` 를 따라가며 필요한 파일을 모두 모은 뒤, 각 파일을 스캐너와 파서에 넘긴다.

### 스캐너

소스코드를 읽어 **토큰** 으로 나누는 어휘 분석(lexical analysis) 단계다. 각 토큰에는 `SyntaxKind` 라는 종류가 붙는다.

```ts
const woowa = "bros";
```

| 토큰      | SyntaxKind         |
| --------- | ------------------ |
| `const`   | `ConstKeyword`     |
| (공백)    | `WhitespaceTrivia` |
| `woowa`   | `Identifier`       |
| `=`       | `EqualsToken`      |
| `"bros"`  | `StringLiteral`    |
| `;`       | `SemicolonToken`   |

### 파서

스캐너가 만든 토큰으로 **AST** 를 만드는 구문 분석(syntax analysis) 단계다. 파서는 토큰을 하나씩 받아 문법 규칙에 맞게 노드로 엮는다.

위 코드는 대략 다음과 같은 트리가 된다.

```
SourceFile
└─ VariableStatement
   └─ VariableDeclarationList (const)
      └─ VariableDeclaration
         ├─ Identifier (woowa)
         └─ StringLiteral ("bros")
```

이 단계에서는 문법만 본다. 괄호가 안 닫혔다 같은 **구문 오류** 는 여기서 잡히지만, 타입이 맞는지는 아직 모른다.

### 바인더

AST 의 선언 노드마다 **심볼** 을 만들어 연결한다. 심볼은 "이 이름이 무엇을 가리키는가" 를 담는 단위로, 같은 이름의 선언이 여러 곳에 흩어져 있어도 하나의 심볼로 묶인다. 바인더는 스코프별 **심볼 테이블** 을 만들고, 심볼에는 무엇으로 선언되었는지를 나타내는 `SymbolFlags` 를 붙인다.

```ts
type SomeType = string | number;

interface SomeInterface {
  name: string;
  age?: number;
}

let foo: string = "LET";

const someObject: SomeInterface = {
  name: "woowa",
  age: 1,
};
```

`SomeType` 은 `TypeAlias`, `SomeInterface` 는 `Interface`, `foo` 는 `BlockScopedVariable` 플래그를 가진 심볼이 된다. 이렇게 이름과 선언이 연결되어 있어야 다음 단계에서 "`someObject` 의 타입이 무엇인지" 를 찾아갈 수 있다.

### 체커와 이미터

**체커** 는 파서가 만든 AST 와 바인더가 만든 심볼을 이용해 타입을 검사한다. 타입스크립트 컴파일러 코드에서 가장 큰 부분(`checker.ts`)이다. 발견한 오류는 진단 정보(diagnostics)로 모아 출력한다.

**이미터** 는 검사가 끝난 AST 를 바탕으로 결과 파일을 만든다.

- `.js`: 타입이 지워지고 `target` 에 맞게 변환된 자바스크립트
- `.d.ts`: 타입 선언 파일 (`declaration` 옵션)
- `.js.map`: 원본 코드와 결과 코드를 잇는 소스맵 (`sourceMap` 옵션)

앞서 본 것처럼 이미터는 체커 결과와 상관없이 동작하므로, `noEmitOnError` 를 켜지 않으면 타입 오류가 있어도 파일이 만들어진다.
