# 7장 비동기 호출

## 7.1 API 요청

### 런타임에서 응답 타입 검증하기

타입스크립트의 타입은 컴파일 후 제거되므로 API 응답에 타입을 지정하더라도 실제 데이터의 형태를 보장하지 않는다.

책에서는 Superstruct를 소개하지만, 2026년 신규 타입스크립트 프로젝트에서는 Zod를 더 일반적인 선택으로 볼 수 있다. Zod는 폼뿐 아니라 API 응답처럼 외부에서 들어오는 데이터를 런타임에 검증하는 용도로도 사용한다.

핵심은 특정 라이브러리보다 외부 데이터를 `unknown`으로 취급하고 애플리케이션의 경계에서 검증하는 것이다.

## 7.3 API 에러 핸들링

| 방법            | 선택하는 경우                                                                               |
| --------------- | ------------------------------------------------------------------------------------------- |
| 타입 가드       | `unknown`으로 받은 에러의 타입을 좁혀 상태 코드나 응답 데이터를 안전하게 확인할 때          |
| 에러 서브클래싱 | 인증 오류, 권한 오류, 네트워크 오류처럼 도메인별 에러를 구분하고 각각 다른 동작을 적용할 때 |
| 인터셉터        | 토큰 만료 처리, 공통 로깅, 공통 응답 변환처럼 모든 API 요청에 반복되는 처리가 있을 때       |
| 에러 바운더리   | 렌더링 중 발생한 예외로 화면 전체가 깨지는 것을 막고 대체 UI를 표시할 때                    |
| React Query     | 요청 실패 상태, 재시도, 에러 UI 등 서버 상태 요청의 생명주기를 관리할 때                    |
| 상태 관리 라이브러리 | 인증 만료나 전역 오류 모달처럼 앱 전체에 영향을 미치는 에러를 여러 컴포넌트에서 공유할 때 |

책의 상태 관리 라이브러리는 Redux 같은 클라이언트 전역 상태 관리를 의미한다. 현재는 일반적인 API 오류 상태는 React Query 같은 서버 상태 관리 라이브러리에 맡기고, 앱 전체에 영향을 주는 오류만 전역 상태로 관리하는 편이 자연스럽다.

```text
API 요청 실패
├─ 에러가 어떤 형태인지 안전하게 확인 → 타입 가드
├─ 에러에 도메인 의미를 부여 → 에러 서브클래싱
├─ 모든 요청에 공통 처리 → 인터셉터
├─ 요청별 실패 상태와 재시도 관리 → React Query
└─ 처리하지 못한 오류의 대체 화면 → 에러 바운더리
```
