## API 요청

### fetch 로 API 요청하기

장바구니 목록을 불러오는 컴포넌트를 `fetch` 로 직접 구현하면 다음과 같다.

```tsx
const CartBadge: React.FC = () => {
  const [cartCount, setCartCount] = useState(0);

  useEffect(() => {
    fetch("https://api.baemin.com/cart")
      .then((response) => response.json())
      .then(({ cartItem }) => {
        setCartCount(cartItem.length);
      });
  }, []);

  return <>{/* cartCount 상태를 이용하여 컴포넌트 렌더링 */}</>;
};
```

장바구니 정보를 쓰는 컴포넌트가 여러 곳이면, 백엔드 URL 이 바뀌거나 요청 방식이 달라질 때 이 코드를 전부 찾아 고쳐야 한다.

### 서비스 레이어로 분리하기

비동기 호출 코드는 컴포넌트에서 떼어 **서비스 레이어** 로 옮긴다. 컴포넌트는 "어떤 데이터가 필요한지" 만 알고, "어떻게 가져오는지" 는 서비스 레이어가 책임진다.

다만 `fetch` 를 함수로 한 번 감싼다고 끝나지 않는다. 타임아웃, 커스텀 헤더, 요청 취소, 에러 처리 같은 공통 요구사항이 생기면 결국 fetch 위에 그 기능을 직접 쌓아야 한다. 그래서 보통 Axios 같은 라이브러리를 쓴다.

### Axios 활용하기

`axios.create` 로 기본 설정이 담긴 인스턴스를 만들어 두고 API 요청은 이 인스턴스로 한다.

```ts
const apiRequester: AxiosInstance = axios.create({
  baseURL: "https://api.baemin.com",
  timeout: 5000,
});

const fetchCart = (): AxiosPromise<FetchCartResponse> =>
  apiRequester.get<FetchCartResponse>("cart");

const postCart = (postCartRequest: PostCartRequest): AxiosPromise<PostCartResponse> =>
  apiRequester.post<PostCartResponse>("cart", postCartRequest);
```

API 엔트리가 여러 개라면 기본 URL 이 다른 인스턴스를 따로 만든다.

```ts
const orderApiRequester: AxiosInstance = axios.create({
  baseURL: "https://api.baemin.or/",
  // ...
});

const orderCartApiRequester: AxiosInstance = axios.create({
  baseURL: "https://cart.baemin.order/",
  // ...
});
```

### Axios 인터셉터 사용하기

인스턴스마다 요청 전·응답 후에 공통으로 처리할 로직을 **인터셉터** 로 끼워 넣을 수 있다. 헤더 설정, 에러 처리 같은 것을 한곳에서 관리한다.

```ts
const setRequestDefaultHeader = (requestConfig: AxiosRequestConfig) => {
  const config = requestConfig;
  config.headers = {
    ...config.headers,
    "Content-Type": "application/json;charset=utf-8",
    user: getUserToken(),
    agent: getAgent(),
  };
  return config;
};

const setOrderRequestDefaultHeader = (requestConfig: AxiosRequestConfig) => {
  const config = requestConfig;
  config.headers = {
    ...config.headers,
    "Content-Type": "application/json;charset=utf-8",
    "order-api-key": "super-secret-key",
  };
  return config;
};

apiRequester.interceptors.request.use(setRequestDefaultHeader);
orderApiRequester.interceptors.request.use(setOrderRequestDefaultHeader);
```

응답 인터셉터도 같은 방식이다. `use(onFulfilled, onRejected)` 로 성공·실패 처리를 각각 넘긴다.

```ts
const httpErrorHandler = (error: AxiosError<ErrorResponse> | Error) => {
  // ...
};

apiRequester.interceptors.response.use(
  (response: AxiosResponse) => response,
  httpErrorHandler
);
```

#### API 빌더 패턴

요청마다 옵션이 조금씩 다르다면 **빌더 패턴** 으로 요청 객체를 조립할 수 있다.

```ts
class API {
  readonly method: HTTPMethod;
  readonly url: string;
  baseURL?: string;
  headers?: HTTPHeaders;
  params?: HTTPParams;
  data?: unknown;
  timeout?: number;
  withCredentials?: boolean;

  constructor(method: HTTPMethod, url: string) {
    this.method = method;
    this.url = url;
  }

  call<T>(): AxiosPromise<T> {
    const http = axios.create();
    // 만약 withCredentials 가 설정되어 있다면 인터셉터 추가
    if (this.withCredentials) {
      http.interceptors.response.use(
        (response) => response,
        (error) => {
          if (error.response && error.response.status === 401) {
            /* 에러 처리 진행 */
          }
          return Promise.reject(error);
        }
      );
    }
    return http.request({ ...this });
  }
}

class APIBuilder {
  private _instance: API;

  constructor(method: HTTPMethod, url: string, data?: unknown) {
    this._instance = new API(method, url);
    this._instance.baseURL = apiHost;
    this._instance.data = data;
    this._instance.headers = { "Content-Type": "application/json; charset=utf-8" };
    this._instance.timeout = 5000;
    this._instance.withCredentials = false;
  }

  static get = (url: string) => new APIBuilder("GET", url);
  static post = (url: string, data: unknown) => new APIBuilder("POST", url, data);

  baseURL(value: string): APIBuilder {
    this._instance.baseURL = value;
    return this;
  }

  withCredentials(value: boolean): APIBuilder {
    this._instance.withCredentials = value;
    return this;
  }

  build(): API {
    return this._instance;
  }
}
```

```ts
const fetchJobNameList = async (name?: string, size?: number) => {
  const api = APIBuilder.get("/apis/web/jobs")
    .withCredentials(true) // 401 응답 시 로그인 페이지로 이동하는 인터셉터 추가
    .params({ name, size })
    .build();
  const { data } = await api.call<Response<JobNameListResponse>>();
  return data;
};
```

필요한 옵션만 체이닝으로 고를 수 있어 호출부는 깔끔해지지만, 옵션이 다양하지 않은 경우에는 보일러플레이트만 늘어난다는 단점이 있다.

### API 응답 타입 지정하기

서버 응답이 공통 형식을 따른다면 하나의 제네릭 타입으로 묶는다.

```ts
interface Response<T> {
  data: T;
  status: string;
  serverDateTime: string;
  errorCode?: string; // FAIL, ERROR
  errorMessage?: string; // FAIL, ERROR
}

const fetchCart = (): AxiosPromise<Response<FetchCartResponse>> =>
  apiRequester.get<Response<FetchCartResponse>>("cart");

const postCart = (
  postCartRequest: PostCartRequest
): AxiosPromise<Response<PostCartResponse>> =>
  apiRequester.post<Response<PostCartResponse>>("cart", postCartRequest);
```

`Response` 타입을 `apiRequester` 안에서 한꺼번에 처리하고 싶을 수 있지만, 그러면 `status` 같은 공통 필드를 보고 처리해야 하는 경우 꺼내 쓰기가 어려워진다. **`Response` 타입은 `apiRequester` 가 모르게 관리** 하는 편이 낫다.

API 마다 응답 타입을 따로 선언해 두면, 지금은 같은 구조라도 나중에 서로 다르게 바뀌었을 때 영향 범위를 줄일 수 있다.

```ts
interface FetchCartResponse {
  cartItems: CartItem[];
}

interface PostCartResponse {
  cartItem: CartItem;
}
```

### 뷰 모델 사용하기

API 응답은 초기 개발 단계에서 자주 바뀐다. 응답 구조를 컴포넌트가 그대로 쓰면, 응답이 바뀔 때마다 그 데이터를 쓰는 컴포넌트를 모두 고쳐야 한다.

```ts
interface ListResponse {
  items: ListItem[];
}

const fetchList = async (filter?: ListFetchFilter): Promise<ListResponse> => {
  const { data } = await api
    .params({ ...filter })
    .get("/apis/get-list-summaries")
    .call<Response<ListResponse>>();

  return { data };
};
```

```tsx
const ListPage: React.FC = () => {
  const [totalItemCount, setTotalItemCount] = useState(0);
  const [items, setItems] = useState<ListItem[]>([]);

  useEffect(() => {
    // 예시를 위한 API 호출과 then 구문
    fetchList(filter).then(({ items }) => {
      setTotalItemCount(items.length);
      setItems(items);
    });
  }, []);

  return (
    <div>
      <Chip label={totalItemCount} />
      <Table items={items} />
    </div>
  );
};
```

이럴 때 응답을 그대로 쓰지 않고 클라이언트에서 쓰기 좋은 **뷰 모델** 로 한 번 변환한다.

```ts
interface JobListItemResponse {
  name: string;
}

interface JobListResponse {
  jobItems: JobListItemResponse[];
}

class JobList {
  readonly totalItemCount: number;
  readonly items: JobListItemResponse[];

  constructor({ jobItems }: JobListResponse) {
    this.totalItemCount = jobItems.length;
    this.items = jobItems;
  }
}

const fetchJobList = async (filter?: ListFetchFilter): Promise<JobListResponse> => {
  const { data } = await api
    .params({ ...filter })
    .get("/apis/get-list-summaries")
    .call<Response<JobListResponse>>();

  return new JobList(data);
};
```

응답 구조가 바뀌어도 뷰 모델의 생성자만 고치면 되고, `totalItemCount` 처럼 클라이언트에서 계산이 필요한 값도 한곳에 모을 수 있다.

단, 추상화 레이어가 하나 더 생기므로 코드가 복잡해지고, 필드가 추가되면 타입·뷰 모델·변환 로직을 모두 손봐야 한다. 그래서 꼭 필요한 곳에만 쓰고, 백엔드와 응답 구조를 협의하거나 **BFF(Backend For Frontend)** 로 프론트엔드에 맞는 응답을 받는 방법도 함께 고려한다.

## API 상태 관리하기

실제 API 를 요청하는 코드에서는 성공·실패·로딩 같은 상태를 함께 관리해야 한다. 로딩 중에는 같은 요청을 다시 보내지 않게 막고, 실패하면 에러 화면을 보여주는 식이다.

### 상태 관리 라이브러리에서 호출하기 (MobX)

상태 관리 라이브러리의 비동기 함수에서 API 를 호출하고 결과를 스토어에 저장하는 방식이다. MobX 는 클래스 안에서 상태와 비동기 액션을 함께 다룬다.

```ts
import { runInAction, makeAutoObservable } from "mobx";
import { observer } from "mobx-react-lite";
import type Job from "models/Job";

type LoadingState = "PENDING" | "DONE" | "ERROR";

class JobStore {
  job: Job[] = [];
  state: LoadingState = "PENDING";
  errorMsg = "";

  constructor() {
    makeAutoObservable(this);
  }

  async fetchJobList() {
    this.job = [];
    this.state = "PENDING";
    this.errorMsg = "";
    try {
      const jobList = await fetchJobList();
      runInAction(() => {
        this.job = jobList;
        this.state = "DONE";
      });
    } catch (e) {
      runInAction(() => {
        this.state = "ERROR";
        this.errorMsg = e.message;
      });
    }
  }
}
```

`await` 이후의 상태 변경은 `runInAction` 으로 감싸야 MobX 가 액션으로 인식한다. 컴포넌트는 스토어를 구독해 상태를 그대로 쓴다.

```tsx
const JobList = observer((): JSX.Element => {
  const [jobStore] = useState(() => new JobStore());

  useEffect(() => {
    jobStore.fetchJobList();
  }, [jobStore]);

  if (jobStore.state === "PENDING") return <Loading />;
  if (jobStore.state === "ERROR") return <Error message={jobStore.errorMsg} />;

  return (
    <ul>
      {jobStore.job.map((job) => (
        <Item key={job.id} job={job} />
      ))}
    </ul>
  );
});
```

이 방식은 API 마다 로딩·에러 상태와 그 처리 로직을 스토어에 직접 만들어 줘야 한다는 부담이 있다.

### 훅으로 호출하기

`react-query` 같은 라이브러리는 API 요청과 그 상태 관리를 훅으로 묶어 준다. 캐시 키를 기준으로 데이터를 캐싱하고, 같은 키의 요청이 여러 번 일어나도 한 번만 호출한다.

```ts
// Job 목록을 불러오는 훅
const useFetchJobList = () => {
  return useQuery(["fetchJobList"], async () => {
    const response = await JobService.fetchJobList();
    // View Model 을 사용해서 결과
    return new JobList(response);
  });
};

// Job 1 개를 업데이트하는 훅
const useUpdateJob = (
  id: number,
  // Job 1 개 update 이후 Query Option
  { onSuccess, ...options }: UseMutationOptions<void, Error, JobUpdateFormValue>
): UseMutationResult<JobUpdateFormValue> => {
  const queryClient = useQueryClient();

  return useMutation(
    ["updateJob", id],
    async (jobUpdateForm: JobUpdateFormValue) => {
      await JobService.updateJob(id, jobUpdateForm);
    },
    {
      onSuccess: (data: void, values: JobUpdateFormValue, context: unknown) => {
        // 성공 시 'fetchJobList' 를 유효하지 않음으로 설정
        queryClient.invalidateQueries(["fetchJobList"]);
        onSuccess && onSuccess(data, values, context);
      },
      ...options,
    }
  );
};
```

`useUpdateJob` 이 성공하면 `invalidateQueries` 로 `fetchJobList` 캐시를 무효화하고, 그 키를 쓰는 컴포넌트는 자동으로 다시 데이터를 받아온다.

```tsx
const JobList: React.FC = () => {
  // 비동기 데이터 필요한 컴포넌트에서 자체 상태로 저장 후 사용
  const {
    isLoading,
    isError,
    error,
    refetch,
    data: jobList,
  } = useFetchJobList();

  // 간단한 Polling 로직, 실시간으로 화면이 갱신돼야 하는 요구가 없어서
  // 30초 간격으로 갱신한다
  useInterval(() => refetch(), 30000);

  // Loading 인 경우에도 화면에 표시해준다
  if (isLoading) return <LoadingSpinner />;

  // Error 에 대한 처리
  if (isError) return <ErrorAlert error={error} />;

  return (
    <>
      {jobList.map((job) => (
        <Job job={job} />
      ))}
    </>
  );
};
```

로딩·에러 상태를 훅이 들고 있으니 컴포넌트에서 별도 상태를 만들 필요가 없다.

> react-query 는 **전역 상태 관리 라이브러리가 아니라 서버 상태를 캐싱하는 라이브러리** 다. 클라이언트에서만 쓰는 전역 상태는 여전히 별도 상태 관리 도구로 다룬다.

## API 에러 핸들링

### 타입 가드 활용하기

서버의 에러 응답 형식을 타입으로 정의하고, 타입 가드로 에러를 좁힌다.

```ts
interface ErrorResponse {
  status: string;
  serverDateTime: string;
  errorCode: string;
  errorMessage: string;
}

function isServerError(error: unknown): error is AxiosError<ErrorResponse> {
  return axios.isAxiosError(error);
}
```

```ts
const onClickDeleteHistoryButton = async (id: string) => {
  try {
    await axios.post("https://....", { id });
    alert("주문 내역이 삭제되었습니다.");
  } catch (error: unknown) {
    if (isServerError(error) && error.response && error.response.data.errorMessage) {
      // 서버 에러일 때의 처리임을 명시적으로 알 수 있다
      setErrorMessage(error.response.data.errorMessage);
      return;
    }
    setErrorMessage("일시적인 에러가 발생했습니다. 잠시 후 다시 시도해주세요");
  }
};
```

`catch` 의 `error` 는 `unknown` 이므로, 타입 가드를 거쳐야 `error.response.data.errorMessage` 에 안전하게 접근할 수 있다.

### 에러 서브클래싱하기

에러 종류가 많아지면 `Error` 를 상속한 **서브클래스** 로 에러를 구분한다. 어떤 에러인지 이름만 봐도 알 수 있고, `instanceof` 로 분기할 수 있다.

```ts
class OrderHttpError extends Error {
  private readonly privateResponse: AxiosResponse<ErrorResponse> | undefined;

  constructor(message?: string, response?: AxiosResponse<ErrorResponse>) {
    super(message);
    this.name = "OrderHttpError";
    this.privateResponse = response;
  }

  get response(): AxiosResponse<ErrorResponse> | undefined {
    return this.privateResponse;
  }
}

class NetworkError extends Error {
  constructor(message = "") {
    super(message);
    this.name = "NetworkError";
  }
}

class UnauthorizedError extends OrderHttpError {
  constructor(message: string, response?: AxiosResponse<ErrorResponse>) {
    super(message, response);
    this.name = "Unauthorized";
  }
}
```

인터셉터에서 응답 상태에 맞는 에러 객체를 만들어 던진다.

```ts
const httpErrorHandler = (error: AxiosError<ErrorResponse> | Error): Promise<Error> => {
  let promiseError: Promise<Error>;

  if (axios.isAxiosError(error)) {
    if (Object.is(error.code, "ECONNABORTED")) {
      promiseError = Promise.reject(new TimeoutError());
    } else if (Object.is(error.message, "Network Error")) {
      promiseError = Promise.reject(new NetworkError(""));
    } else {
      const { response } = error as AxiosError<ErrorResponse>;
      switch (response?.status) {
        case HttpStatusCode.UNAUTHORIZED:
          promiseError = Promise.reject(new UnauthorizedError(response.data.errorMessage, response));
          break;
        default:
          promiseError = Promise.reject(new OrderHttpError(error.message, error.response));
      }
    }
  } else {
    promiseError = Promise.reject(error);
  }

  return promiseError;
};
```

호출부에서는 `instanceof` 로 에러 종류를 판별한다.

```ts
const onClickDeleteHistoryButton = async (id: string) => {
  try {
    await fetchOrderHistory(id);
  } catch (error) {
    if (error instanceof OrderHttpError) {
      // 주문 API 에러 처리
    }
    if (error instanceof NetworkError) {
      // 네트워크 에러 처리
    }
  }
};
```

### 인터셉터를 활용한 에러 처리

모든 요청에 공통으로 적용할 에러 처리는 응답 인터셉터에 둔다. 예를 들어 401 이면 로그인 페이지로 보낸다.

```ts
const httpErrorHandler = (error: AxiosError<ErrorResponse> | Error): Promise<Error> => {
  // 401 에러인 경우 로그인 페이지로 이동
  if (axios.isAxiosError(error) && error.response?.status === 401) {
    window.location.href = `${backOfficeAuthHost}/login?targetUrl=${window.location.href}`;
  }
  return Promise.reject(error);
};

orderApiRequester.interceptors.response.use(
  (response: AxiosResponse) => response,
  httpErrorHandler
);
```

### 에러 바운더리를 활용한 에러 처리

렌더링 중 하위 컴포넌트에서 던진 에러는 **에러 바운더리** 로 잡아 대체 UI 를 보여준다. 에러가 컴포넌트 트리 전체를 깨뜨리지 않게 막는 역할이다.

```tsx
interface ErrorBoundaryProps {
  children: React.ReactNode;
}

interface ErrorBoundaryState {
  hasError: boolean;
}

class ErrorBoundary extends React.Component<ErrorBoundaryProps, ErrorBoundaryState> {
  constructor(props: ErrorBoundaryProps) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(): ErrorBoundaryState {
    return { hasError: true };
  }

  componentDidCatch(error: Error, errorInfo: React.ErrorInfo): void {
    this.setState({ hasError: true });
    console.error(error, errorInfo);
  }

  render(): React.ReactNode {
    const { children } = this.props;
    const { hasError } = this.state;

    return hasError ? <ErrorPage /> : children;
  }
}
```

```tsx
const App = () => {
  return (
    <ErrorBoundary>
      <OrderHistoryPage />
    </ErrorBoundary>
  );
};
```

`OrderHistoryPage` 안에서 처리되지 않은 에러가 나면 `ErrorPage` 가 대신 렌더링된다.

### react-query 를 활용한 에러 처리

react-query 훅은 `isError`, `error` 를 함께 돌려주므로 컴포넌트에서 바로 분기할 수 있다.

```tsx
const JobComponent: React.FC = () => {
```

### 그 밖의 에러 처리

HTTP 상태 코드는 200 인데 응답 본문으로 실패를 알리는 API 도 있다.

```ts
{
  "status": "C20005", // 비즈니스 로직 에러코드
  "message": "장바구니에 품절된 메뉴가 있습니다."
}
```

이런 경우에도 앞에서처럼 커스텀 에러 클래스를 만들고, 응답 인터셉터에서 본문을 확인해 에러로 던지면 일반 에러와 같은 흐름으로 처리할 수 있다.

```ts
const successHandler = (response: AxiosResponse<CommonResponse>) => {
  const { status, message } = response.data;

  if (status === "C20005") {
    return Promise.reject(new CustomResponseError(message, response));
  }
  return response;
};

orderApiRequester.interceptors.response.use(successHandler, httpErrorHandler);
```

```ts
const createOrder = async (data: OrderData) => {
  try {
    await orderApiRequester.post("https://...", data);
  } catch (error) {
    if (error instanceof CustomResponseError) {
      // 비즈니스 로직 에러 처리
    }
  }
};
```

## API 모킹

백엔드 API 가 아직 없거나, 특정 응답(에러·빈 목록 등)을 재현하기 어려울 때 **모킹** 으로 프론트엔드 개발을 먼저 진행할 수 있다.

### JSON 파일 불러오기

가장 간단한 방법은 응답 예시를 JSON 파일로 만들어 두고 그 경로로 요청하는 것이다.

```ts
// service.ts
const SERVICES: Service[] = [
  {
    id: 0,
    name: "배달의민족",
  },
  {
    id: 1,
    name: "만화경",
  },
];

export default SERVICES;

// api.ts
const getServices = ApiRequester.get("/mock/service.json");
```

설정이 필요 없어 빠르게 쓸 수 있지만, 요청에 따라 응답을 바꾸는 등 실제 API 처럼 동작하게 만들 수는 없다.

### NextApiHandler 활용하기

Next.js 를 쓴다면 API 라우트에 목 핸들러를 만들 수 있다. 응답 로직을 코드로 짤 수 있어 JSON 파일보다 유연하다.

```ts
// api/mock/brand
import { NextApiHandler } from "next";

const BRANDS: Brand[] = [
  {
    id: 1,
    label: "배민스토어",
  },
  {
    id: 2,
    label: "비마트",
  },
];

const handler: NextApiHandler = (req, res) => {
  // request 유효성 검증

  res.json(BRANDS);
};

export default handler;
```

### API 요청 핸들러에 분기 추가하기

요청 함수에 목 사용 여부를 받아, 목 URL 과 실제 URL 중 하나로 보낸다.

```ts
const mockFetchBrands = (): Promise<FetchBrandsResponse> =>
  new Promise((resolve) => {
    setTimeout(() => {
      resolve({
        status: "SUCCESS",
        message: null,
        data: [
          { id: 1, label: "배민스토어" },
          { id: 2, label: "비마트" },
        ],
      });
    }, 500);
  });

const fetchBrands = () => {
  if (useMock) {
    return mockFetchBrands();
  }

  return requester.get("/brands");
};
```

개발 중 필요한 순간에 목으로 바꿔 쓸 수 있지만, 모든 요청 함수에 분기가 들어가고 목 사용이 끝나면 분기 코드를 다시 정리해야 한다.

### axios-mock-adapter 로 모킹하기

`axios-mock-adapter` 는 Axios 요청을 가로채 지정한 응답을 돌려준다. 요청 함수는 그대로 두고 목 설정만 따로 관리할 수 있다.

```ts
// mock/index.ts
import axios from "axios";
import MockAdapter from "axios-mock-adapter";
import fetchOrderListSuccessResponse from "./fetchOrderListSuccessResponse.json";

const mock = new MockAdapter(axios, { onNoMatch: "passthrough" });

export const fetchOrderListMock = () =>
  mock.onGet(/\/order\/list/).reply(200, fetchOrderListSuccessResponse);

// fetchOrderListSuccessResponse.json
{
  "data": [
    {
      "orderNo": "ORDER1234",
      "orderDate": "2022-02-02",
      "shop": {
        "shopNo": "SHOP1234",
        "name": "가게이름1234"
      },
      "deliveryStatus": "DELIVERY"
    }
  ]
}
```

`onNoMatch: "passthrough"` 를 주면 목을 정의하지 않은 요청은 실제 서버로 그대로 나간다.

응답 데이터를 함수로 만들어 두면 요청 파라미터에 따라 다른 응답을 줄 수 있다. 페이지네이션처럼 파라미터마다 결과가 달라지는 경우에 유용하다.

```ts
// mock/index.ts
type MockResponse = [status: number, data: unknown];

export const lazyData = (
  status = 200,
  successData: unknown = defaultSuccessData,
  failData: unknown = defaultFailData,
  time = Math.floor(Math.random() * 1000)
): Promise<MockResponse> =>
  new Promise((resolve) => {
    setTimeout(() => {
      resolve([status, status === 200 ? successData : failData]);
    }, time);
  });

export const fetchOrderListMock = () =>
  mock.onGet(/\/order\/list/).reply(() => lazyData(200, fetchOrderListSuccessResponse));
```

`lazyData` 처럼 지연 시간을 주면 로딩 상태도 확인할 수 있고, 상태 코드를 바꿔 에러 상황도 재현할 수 있다.

### 목업 사용 여부 제어하기

로컬 개발에서만 목을 쓰고 프로덕션에서는 쓰지 않도록 환경 변수로 제어한다.

```ts
interface MockOptions {
  status?: number;
  time?: number;
  use?: boolean;
}

const useMock = Object.is(process.env.REACT_APP_MOCK, "true");

const mockFn = ({ status = 200, time = 100, use = true }: MockOptions) =>
  use &&
  mock
    .onGet(/\/order\/list/)
    .reply(() => lazyData(status, fetchOrderListSuccessResponse, undefined, time));
```

`status`·`time` 을 바꿔 가며 성공·실패·지연 상황을 원하는 대로 만들 수 있다. 목 코드 자체가 번들에 들어가지 않게 하려면 개발 환경에서만 불러온다.

```ts
if (process.env.NODE_ENV === "development" && useMock) {
  import("./mock").then(({ injectMockApi }) => injectMockApi());
}
```

목 코드를 동적 `import` 로 불러오면 프로덕션 빌드에서는 해당 분기가 제거되어, 목 데이터와 `axios-mock-adapter` 가 번들에 포함되지 않는다.
