## 타입 좁히기 - 타입 가드

### 타입 가드란?

타입 좁히기는 변수나 표현식의 타입을 더 작은 범위로 좁혀 나가는 과정이다. 타입을 좁혀야 분기마다 정확한 타입으로 안전하게 코드를 작성할 수 있다.

타입 정보는 컴파일이 끝나면 사라진다. 그래서 런타임에 `if` 문으로 타입을 검사하려면 **자바스크립트 연산자**를 써야 한다. 타입스크립트는 이 조건문을 보고 블록 안의 타입을 좁혀 준다. 이렇게 타입을 좁히는 조건 검사를 타입 가드라고 한다.

타입 가드는 크게 두 가지다.

- 자바스크립트 연산자를 사용한 타입 가드: `typeof`, `instanceof`, `in`
- 사용자 정의 타입 가드: `is` 키워드로 직접 만든 함수

### typeof - 원시 타입 좁히기

`typeof` 는 원시 타입을 좁힐 때 쓴다. 판별할 수 있는 타입은 `string`, `number`, `boolean`, `undefined`, `object`, `function`, `bigint`, `symbol` 이다.

```ts
const replaceHyphen: (date: string | Date) => string | Date = (date) => {
  if (typeof date === "string") {
    // 이 블록에서 date 는 string
    return date.replace(/-/g, "/");
  }

  return date;
};
```

`null` 과 배열도 `typeof` 결과가 `"object"` 라서 객체 타입을 구분하는 데는 쓸 수 없다.

### instanceof - 인스턴스화된 객체 타입 좁히기

`instanceof` 는 어떤 값이 특정 클래스(생성자)의 인스턴스인지 검사한다.

```ts
interface Range {
  start: Date;
  end: Date;
}

interface DatePickerProps {
  selectedDates?: Date | Range;
}

const DatePicker = ({ selectedDates }: DatePickerProps) => {
  const [selected, setSelected] = useState(convertToRange(selectedDates));
  // ...
};

export function convertToRange(selected?: Date | Range): Range | undefined {
  return selected instanceof Date
    ? { start: selected, end: selected }
    : selected;
}
```

`Range` 는 인터페이스라서 런타임에 존재하지 않는다. 그래서 `selected instanceof Range` 는 쓸 수 없고, 실제 클래스인 `Date` 로 검사한다.

DOM 이벤트에서도 자주 쓴다. `event.target` 은 `EventTarget` 타입이라 `blur()` 같은 메서드를 바로 부를 수 없다.

```ts
const onKeyDown = (event: React.KeyboardEvent) => {
  if (event.target instanceof HTMLInputElement && event.key === "Enter") {
    // 이 블록에서 event.target 은 HTMLInputElement
    event.target.blur();
    onCTAButtonClick(event);
  }
};
```

### in - 객체의 속성 유무로 좁히기

`A in B` 는 B 객체에 A 속성이 있는지 검사한다. 속성의 값이 아니라 **속성이 있는지 없는지**만 본다. 그래서 값이 `undefined` 여도 속성이 있으면 `true` 다.

```ts
interface BasicNoticeDialogProps {
  noticeTitle: string;
  noticeBody: string;
}

interface NoticeDialogWithCookieProps extends BasicNoticeDialogProps {
  cookieKey: string;
  noForADay?: boolean;
  neverAgain?: boolean;
}

export type NoticeDialogProps =
  | BasicNoticeDialogProps
  | NoticeDialogWithCookieProps;

const NoticeDialog: React.FC<NoticeDialogProps> = (props) => {
  if ("cookieKey" in props) return <NoticeDialogWithCookie {...props} />;
  return <NoticeDialogBase {...props} />;
};
```

`cookieKey` 가 있으면 `NoticeDialogWithCookieProps` 로, 없으면 `BasicNoticeDialogProps` 로 좁혀진다. 여러 객체 타입을 유니온으로 받는 컴포넌트에서 props 로 분기할 때 유용하다.

### is - 사용자 정의 타입 가드

`A is B` 형식으로 반환 타입을 선언하면, 함수가 `true` 를 돌려줄 때 A 를 B 타입으로 좁혀 준다. 이런 반환 타입을 타입 명제(type predicate)라고 한다.

```ts
const DESTINATION_CODE_LIST = ["TOKYO", "PARIS", "NEWYORK"] as const;
type DestinationCode = (typeof DESTINATION_CODE_LIST)[number];

const isDestinationCode = (x: string): x is DestinationCode =>
  DESTINATION_CODE_LIST.includes(x as DestinationCode);

const getAvailableDestinationNameList = async (): Promise<DestinationName[]> => {
  const data = await AxiosRequest<string[]>("get", ".../destinations");
  const destinationNames: DestinationName[] = [];

  data?.forEach((str) => {
    if (isDestinationCode(str)) {
      // str 은 DestinationCode
      destinationNames.push(DestinationNameSet[str]);
    }
  });

  return destinationNames;
};
```

반환 타입을 `boolean` 으로 선언하면 함수 안에서 무슨 검사를 했는지 타입스크립트가 알 수 없다. 그래서 `if (isDestinationCode(str))` 안에서도 `str` 은 계속 `string` 이고 `DestinationNameSet[str]` 에서 에러가 난다.

참고로 TypeScript 5.5 부터는 `(x: unknown) => typeof x === "string"` 처럼 단순한 함수는 `x is string` 을 자동으로 추론해 준다. 하지만 위의 `includes` 검사처럼 추론할 수 없는 경우가 많아서, 좁히는 게 목적이라면 `is` 를 직접 적어 두는 편이 확실하다.

`is` 는 타입스크립트가 검사 내용을 확인하지 않고 개발자의 말을 믿는다는 점도 기억해야 한다. 함수 안의 검사가 틀려도 에러가 나지 않으니, 사실상 `as` 와 같은 책임이 따른다.

## 타입 좁히기 - 식별할 수 있는 유니온

### 에러 정의하기

배민 선물하기 서비스는 에러를 텍스트, 토스트, 얼럿 세 가지 방식으로 보여 준다.

```ts
type TextError = {
  errorCode: string;
  errorMessage: string;
};

type ToastError = {
  errorCode: string;
  errorMessage: string;
  toastShowDuration: number; // 토스트를 띄울 시간
};

type AlertError = {
  errorCode: string;
  errorMessage: string;
  onConfirm: () => void; // 얼럿 창의 확인 버튼을 누른 뒤 액션
};

type ErrorFeedbackType = TextError | ToastError | AlertError;

const errorArr: ErrorFeedbackType[] = [
  { errorCode: "100", errorMessage: "텍스트 에러" },
  { errorCode: "200", errorMessage: "토스트 에러", toastShowDuration: 3000 },
  { errorCode: "300", errorMessage: "얼럿 에러", onConfirm: () => {} },
];
```

문제는 `toastShowDuration` 과 `onConfirm` 을 **둘 다** 가진 객체도 에러 없이 들어간다는 것이다.

```ts
const errorArr: ErrorFeedbackType[] = [
  // 에러가 나지 않는다
  {
    errorCode: "999",
    errorMessage: "잘못된 에러",
    toastShowDuration: 3000,
    onConfirm: () => {},
  },
];
```

이 객체는 `ToastError` 로도, `AlertError` 로도 볼 수 있어서 통과한다. 자바스크립트는 덕 타이핑 언어라서 필요한 속성만 있으면 해당 타입으로 인정하기 때문이다.

### 식별할 수 있는 유니온

식별할 수 있는 유니온(Discriminated Unions)은 타입마다 구분할 수 있는 판별자를 달아 주는 방식이다. 판별자는 각 타입에서 서로 다른 리터럴 값을 가진다.

```ts
type TextError = {
  errorType: "TEXT";
  errorCode: string;
  errorMessage: string;
};

type ToastError = {
  errorType: "TOAST";
  errorCode: string;
  errorMessage: string;
  toastShowDuration: number;
};

type AlertError = {
  errorType: "ALERT";
  errorCode: string;
  errorMessage: string;
  onConfirm: () => void;
};

const errorArr: ErrorFeedbackType[] = [
  {
    errorType: "TEXT",
    errorCode: "999",
    errorMessage: "잘못된 에러",
    toastShowDuration: 3000,
    // Object literal may only specify known properties,
    // and 'toastShowDuration' does not exist in type 'TextError'.
    onConfirm: () => {},
  },
];
```

이제 `errorType` 으로 어떤 타입인지 정해지므로, 그 타입에 없는 속성을 넣으면 에러가 난다. 분기할 때도 `errorType` 만 비교하면 타입이 좁혀진다.

```ts
function showError(error: ErrorFeedbackType) {
  switch (error.errorType) {
    case "TOAST":
      showToast(error.errorMessage, error.toastShowDuration); // ToastError
      break;
    case "ALERT":
      showAlert(error.errorMessage, error.onConfirm); // AlertError
      break;
  }
}
```

### 판별자 선정 시 주의점

판별자는 **유닛 타입**으로 선언돼야 제대로 동작한다. 유닛 타입은 오직 하나의 값만 가지는 타입으로, `"a"` 나 `1` 같은 리터럴 타입과 `null`, `undefined` 가 여기에 속한다.

- 판별자의 값은 리터럴 타입이어야 한다.
- 판별자 값에 적어도 하나 이상의 유닛 타입이 포함돼야 하며, `string`, `Error` 처럼 여러 값을 가질 수 있는(인스턴스화할 수 있는) 타입은 포함되지 않아야 한다.

```ts
interface A {
  value: "a"; // 유닛 타입
  answer: 1;
}

interface B {
  value: string; // 유닛 타입이 아님
  answer: 2;
}

interface C {
  value: Error; // 인스턴스화할 수 있는 타입
  answer: 3;
}

type Unions = A | B | C;

function handle(param: Unions) {
  if (param.value === "a") {
    param.answer; // 1 | 2
  }

  if (param.answer === 1) {
    param.value; // "a"
  }
}
```

`value === "a"` 로 비교했는데 `A` 로 좁혀지지 않는다. `B` 의 `value` 가 `string` 이라서 `"a"` 도 될 수 있기 때문이다. 반면 `answer` 는 모든 타입이 유닛 타입이라 `answer === 1` 이면 정확히 `A` 로 좁혀진다. 판별자를 고를 때는 모든 타입에서 겹치지 않는 리터럴 값을 가진 속성을 골라야 한다.

## Exhaustiveness Checking으로 정확한 타입 분기 유지하기

### 상품권 가격 예시

Exhaustiveness Checking 은 모든 케이스에 대해 철저하게 분기 처리를 했는지 타입으로 검사하는 방법이다.

```ts
type ProductPrice = "10000" | "20000";

const getProductName = (productPrice: ProductPrice): string => {
  if (productPrice === "10000") return "배민상품권 1만 원";
  if (productPrice === "20000") return "배민상품권 2만 원";
  else {
    return "배민상품권";
  }
};
```

여기에 5천 원 상품권이 새로 추가되면 `ProductPrice` 만 바꾸고 `getProductName` 은 고치는 걸 잊기 쉽다. 이때 에러가 나지 않아서 5천 원 상품권은 조용히 `"배민상품권"` 으로 표시된다.

### never 로 누락 잡기

```ts
type ProductPrice = "10000" | "20000" | "5000";

const exhaustiveCheck = (param: never) => {
  throw new Error("type error!");
};

const getProductName = (productPrice: ProductPrice): string => {
  if (productPrice === "10000") return "배민상품권 1만 원";
  if (productPrice === "20000") return "배민상품권 2만 원";
  else {
    exhaustiveCheck(productPrice);
    // Argument of type '"5000"' is not assignable to parameter of type 'never'.
    return "배민상품권";
  }
};
```

모든 케이스를 처리했다면 `else` 블록에 도달한 `productPrice` 는 남은 타입이 없으므로 `never` 가 된다. 처리하지 않은 케이스가 있으면 그 타입(`"5000"`)이 남아서 `never` 매개변수에 넘길 수 없다. 그래서 컴파일 단계에서 누락을 알 수 있다.

3장에서 정리한 "never 에는 never 자신 말고 아무것도 할당할 수 없다" 는 성질을 그대로 활용한 것이다. 이 방법은 유니온 타입에 값이 추가될 때 처리해야 할 모든 곳을 에러로 알려 주므로, 앞에서 본 식별할 수 있는 유니온의 `switch` 문과 함께 쓰면 좋다.
