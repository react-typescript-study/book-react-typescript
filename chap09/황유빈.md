## 리액트 훅

훅은 함수 컴포넌트에서 상태, 생명주기와 관련된 동작 등 리액트의 기능을 사용할 수 있게 해주는 함수다. 타입스크립트와 함께 쓰면 상태에 저장할 값, 이벤트 핸들러의 인자, ref 가 가리키는 대상 등을 컴파일타임에 검사할 수 있다.

### 훅을 사용할 때 지켜야 하는 규칙

- 함수 컴포넌트나 커스텀 훅의 **최상위** 에서 호출한다.
- 조건문, 반복문, 이벤트 핸들러, 조기 반환 뒤에서 호출하지 않는다.
- 일반 자바스크립트 함수나 클래스 컴포넌트에서는 호출하지 않는다.

리액트는 렌더링마다 훅의 호출 순서를 기준으로 상태를 연결한다. 조건에 따라 훅을 건너뛰면 순서가 달라지므로, 조건은 훅 내부에서 처리한다.

```tsx
import { useEffect } from "react";

function PageTitle({ enabled }: { enabled: boolean }) {
  useEffect(() => {
    if (!enabled) return;

    const previousTitle = document.title;
    document.title = "주문 내역";

    return () => {
      document.title = previousTitle;
    };
  }, [enabled]);

  return <h1>주문 내역</h1>;
}
```

타입 검사만으로 훅 규칙 위반이나 의존성 누락을 모두 잡을 수는 없다. `eslint-plugin-react-hooks` 로 함께 검사한다. [리액트 훅 규칙](https://react.dev/reference/rules/rules-of-hooks)

### useState: 상태의 타입 지정하기

`useState` 는 현재 상태와 상태를 변경하는 함수를 튜플로 반환한다. 초기값이 명확하면 타입을 추론한다.

```tsx
const [count, setCount] = useState(0); // number
const [name, setName] = useState(""); // string

setCount(1);
// setCount("1"); // 타입 오류
```

초기값만으로 앞으로 저장할 값까지 표현할 수 없으면 제네릭을 지정한다.

```tsx
interface User {
  id: number;
  name: string;
}

const [user, setUser] = useState<User | null>(null);
const [users, setUsers] = useState<User[]>([]);
const [status, setStatus] = useState<"idle" | "loading" | "success">("idle");

setUser({ id: 1, name: "유빈" });
setStatus("loading");
// setStatus("done"); // 타입 오류
```

`useState(null)` 만 쓰면 상태가 `null` 로 추론되어 나중에 사용자 객체를 넣을 수 없다. 빈 배열도 strict 설정에서는 `never[]` 로 추론될 수 있으므로, 원소 타입을 알려준다.

#### 상태 변경 함수의 타입

초기값을 받는 `useState` 의 핵심 타입 구조는 다음과 같다.

```ts
type SetStateAction<S> = S | ((prevState: S) => S);
type Dispatch<A> = (value: A) => void;

declare function useState<S>(
  initialState: S | (() => S)
): [S, Dispatch<SetStateAction<S>>];
```

상태 변경 함수에는 **새 값** 또는 **이전 상태로 새 값을 계산하는 함수** 를 전달할 수 있다.

```tsx
setCount(3);
setCount((previous) => previous + 1);
```

이전 상태를 바탕으로 변경할 때는 함수형 업데이트를 사용한다. setter 를 호출해도 현재 실행 중인 함수 안의 상태 변수가 즉시 바뀌지는 않는다.

객체나 배열은 직접 수정하지 않고 새 값으로 교체한다.

```tsx
setUsers((previous) => [...previous, { id: 2, name: "혜림" }]);
setUser((previous) =>
  previous === null ? null : { ...previous, name: "새 이름" }
);
```

#### 지연 초기화

초기값 계산에 비용이 든다면 함수를 전달한다.

```tsx
const [items] = useState(() => {
  return Array.from({ length: 1000 }, (_, index) => index);
});
```

리액트는 초기 상태를 만들 때 이 함수를 호출한다. 초기화 함수는 순수해야 하며, 개발 환경의 Strict Mode 에서는 순수성을 확인하기 위해 두 번 호출될 수 있다. [useState 문서](https://react.dev/reference/react/useState)

### useEffect: 외부 시스템과 동기화하기

`useEffect` 는 이벤트 구독, 타이머 등 컴포넌트 외부와 연결되는 작업에 사용한다. 콜백은 아무것도 반환하지 않거나, 연결을 해제하는 **클린업 함수** 를 반환한다.

```tsx
import { useEffect, useState } from "react";

function Timer({ intervalMs }: { intervalMs: number }) {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timerId = window.setInterval(() => {
      setCount((previous) => previous + 1);
    }, intervalMs);

    return () => {
      window.clearInterval(timerId);
    };
  }, [intervalMs]);

  return <p>{count}회</p>;
}
```

`intervalMs` 가 바뀌면 이전 타이머를 정리한 뒤 새 타이머를 만든다. 컴포넌트가 제거될 때도 정리한다.

| 의존성 배열 | 실행 시점 |
| --- | --- |
| 생략 | 매 커밋 후 |
| `[]` | 마운트 후. 의존성 변화로 다시 실행되지는 않음 |
| `[value]` | 마운트 후, 이후 `value` 가 이전과 달라진 커밋 후 |

의존성은 `Object.is` 로 비교한다. Effect 안에서 사용하는 props, state 등 반응형 값은 의존성에 포함한다. 누락하면 과거 렌더링의 값을 계속 참조하는 문제가 생길 수 있다.

> `[]` 라고 해서 항상 딱 한 번만 실행되는 것은 아니다. 개발 환경의 Strict Mode 에서는 설정과 정리가 올바르게 짝을 이루는지 확인하기 위해 추가 실행이 일어날 수 있다.

#### 비동기 함수 사용하기

`async` 함수는 `Promise` 를 반환하므로 Effect 콜백에 직접 전달하지 않는다. 내부에 비동기 함수를 만들고 호출한다.

```tsx
function Notice({ loadMessage }: { loadMessage: () => Promise<string> }) {
  const [message, setMessage] = useState("");

  useEffect(() => {
    let ignore = false;

    const load = async () => {
      try {
        const result = await loadMessage();
        if (!ignore) setMessage(result);
      } catch {
        if (!ignore) setMessage("메시지를 불러오지 못했습니다.");
      }
    };

    void load();

    return () => {
      ignore = true;
    };
  }, [loadMessage]);

  return <p>{message}</p>;
}
```

클린업 이후 도착한 결과는 무시한다. 이 처리가 요청 자체를 취소하는 것은 아니다. 또한 부모가 `loadMessage` 를 매번 새 함수로 전달하면 Effect 도 다시 실행된다. [useEffect 문서](https://react.dev/reference/react/useEffect)

### useLayoutEffect: 화면이 그려지기 전에 실행하기

`useLayoutEffect` 는 DOM 이 반영된 뒤, 브라우저가 화면을 그리기 전에 실행된다. 요소의 크기를 측정한 결과를 바로 반영해야 하는 경우에 사용한다.

```tsx
import { useLayoutEffect, useRef, useState } from "react";

function MeasuredBox() {
  const boxRef = useRef<HTMLDivElement>(null);
  const [height, setHeight] = useState(0);

  useLayoutEffect(() => {
    const element = boxRef.current;
    if (element) setHeight(element.getBoundingClientRect().height);
  }, []);

  return (
    <>
      <div ref={boxRef}>크기를 측정할 내용</div>
      <p>처음 측정한 높이: {height}px</p>
    </>
  );
}
```

화면 그리기를 막으므로 오래 걸리는 작업에는 적합하지 않다. 일반적인 동기화 작업에는 `useEffect` 를 쓰고, 화면이 그려지기 전 측정이 필요한 경우에만 사용한다. 두 Effect 모두 서버 렌더링 중에는 실행되지 않는다. [useLayoutEffect 문서](https://react.dev/reference/react/useLayoutEffect)

### useMemo: 계산 결과를 재사용하기

`useMemo` 는 의존성이 같을 때 이전 계산 결과를 재사용한다. 반환 타입은 콜백의 반환값에서 추론한다.

```tsx
import { useMemo } from "react";

interface Product {
  id: number;
  name: string;
  price: number;
}

function ProductTotal({ products }: { products: Product[] }) {
  const total = useMemo(
    () => products.reduce((sum, product) => sum + product.price, 0),
    [products]
  ); // number

  return <p>합계: {total}원</p>;
}
```

`useMemo<number>(...)` 처럼 반환 타입을 명시할 수도 있지만 추론이 충분하면 생략한다. `products` 가 매번 새 배열이면 내용이 같아도 다시 계산한다.

**성능 최적화를 위한 도구** 이므로, 제거해도 코드의 동작은 올바르게 유지되어야 한다. 간단한 계산까지 모두 감싸기보다는 비용이 큰 계산이나 참조 유지가 필요한 곳에 적용한다. [useMemo 문서](https://react.dev/reference/react/useMemo)

### useCallback: 함수 참조를 재사용하기

`useCallback` 은 의존성이 같을 때 이전 함수 참조를 반환한다. 함수를 실행하거나 실행 결과를 저장하는 훅은 아니다.

```tsx
import { useCallback, useState } from "react";
import type { ChangeEventHandler } from "react";

function SearchInput() {
  const [keyword, setKeyword] = useState("");

  const handleChange = useCallback<ChangeEventHandler<HTMLInputElement>>(
    (event) => {
      setKeyword(event.currentTarget.value);
    },
    []
  );

  return <input value={keyword} onChange={handleChange} />;
}
```

제네릭에 함수 타입을 지정하면 `event` 도 입력 요소의 변경 이벤트로 추론된다. 매개변수에 `ChangeEvent<HTMLInputElement>` 를 직접 붙여도 된다.

위 예제는 타입 지정 방법을 보여주기 위한 것으로, 단순한 input 핸들러에 반드시 `useCallback` 이 필요한 것은 아니다. `memo` 로 감싼 자식에게 함수를 전달하거나 다른 훅의 의존성으로 사용할 때 참조 유지가 도움이 될 수 있다. **`useCallback` 만으로 자식의 재렌더링을 막지는 않는다.** [useCallback 문서](https://react.dev/reference/react/useCallback)

### useRef: DOM 이나 렌더링과 무관한 값 보관하기

`useRef` 는 `{ current: 값 }` 형태의 객체를 반환한다. 같은 컴포넌트가 다시 렌더링되어도 객체는 유지되며, `current` 를 바꿔도 재렌더링되지 않는다.

```tsx
import { useRef } from "react";

function FocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>입력창으로 이동</button>
    </>
  );
}
```

DOM 이 연결되기 전이나 제거된 뒤에는 `current` 가 `null` 일 수 있으므로 확인 후 접근한다. 값 변경을 화면에 보여줘야 한다면 ref 대신 state 를 사용한다. [useRef 문서](https://react.dev/reference/react/useRef)

#### RefObject 와 MutableRefObject

React 18 타입 정의에서 대표적인 `useRef` 오버로드는 다음과 같다.

```ts
interface RefObject<T> {
  readonly current: T | null;
}

interface MutableRefObject<T> {
  current: T;
}

declare function useRef<T>(initialValue: T): MutableRefObject<T>;
declare function useRef<T>(initialValue: T | null): RefObject<T>;
```

`strictNullChecks` 를 사용하는 React 18 환경에서는 제네릭에 `null` 을 포함하는지에 따라 선택되는 오버로드가 달라진다.

```tsx
const domRef = useRef<HTMLInputElement>(null);
// RefObject<HTMLInputElement>: current 는 readonly

const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
// MutableRefObject<ReturnType<typeof setTimeout> | null>
// current 에 타이머 ID 를 직접 저장할 수 있다
```

DOM 연결은 리액트가 담당하고, 타이머 ID 같은 값은 코드에서 직접 관리한다. `readonly` 는 타입 수준의 제약이며 런타임에 객체를 동결하는 것은 아니다.

> React 19 타입 정의에서는 ref 가 기본적으로 수정 가능하고 `useRef` 에 초기 인자가 필요하다. 따라서 **`useRef<T>(null)` 의 current 는 언제나 readonly 라고 외우면 안 된다.** 프로젝트의 `@types/react` 버전에 맞춰 이해한다. [React 19 타입 변경 사항](https://react.dev/blog/2024/04/25/react-19-upgrade-guide#typescript-changes)

## 추가 학습: useEffect 와 useLayoutEffect 의 차이

두 훅을 구분하는 핵심은 **화면이 보이기 전에 작업을 끝내야 하는가** 이다.

| 구분 | useEffect | useLayoutEffect |
| --- | --- | --- |
| 실행 기준 | DOM 반영 후, 일반적으로 브라우저가 화면을 먼저 그리도록 허용 | DOM 반영 후, 브라우저가 화면을 그리기 전 |
| 화면 표시와의 관계 | Paint 전 완료를 보장하지 않음 | 실행과 그 안의 상태 업데이트가 Paint 를 막음 |
| 대표 용도 | 이벤트 구독, 타이머, 외부 시스템 동기화 | DOM 크기 측정 후 툴팁 위치 보정 |

### 툴팁 위치 보정으로 이해하기

툴팁을 올바른 위치에 표시하려면 먼저 DOM 을 만든 뒤 실제 높이를 측정해야 하는 경우가 있다.

`useEffect` 에서 높이를 측정하고 위치를 수정하면, 처음 위치가 화면에 보인 뒤 보정될 수 있다.

```text
DOM 반영 → 처음 위치 표시 → 높이 측정·위치 수정 → 보정된 위치 표시
```

`useLayoutEffect` 에서 같은 작업을 하면, 보정을 끝낸 뒤 화면을 보여준다.

```text
DOM 반영 → 높이 측정·위치 수정 → 보정된 위치 표시
```

사용자가 툴팁이 순간적으로 움직이는 모습을 보지 않게 하려면 `useLayoutEffect` 를 사용한다. 대신 작업이 오래 걸리면 화면 표시도 늦어진다. [useLayoutEffect 공식 문서](https://react.dev/reference/react/useLayoutEffect)

### 실행 시점에서 헷갈리지 말아야 할 점

**DOM 반영과 리플로우 완료는 다른 시점** 이다. DOM 의 스타일 값을 변경했다고 해서 브라우저가 실제 크기와 위치 계산까지 즉시 끝낸 것은 아니다.

`useLayoutEffect` 안에서 `getBoundingClientRect()` 로 크기를 읽으면, 브라우저가 필요한 Layout(리플로우)을 그 자리에서 계산할 수 있다. 따라서 두 훅의 공통점을 “리플로우 이후 실행”으로 이해하면 안 된다. [브라우저의 강제 동기 Layout 설명](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)

또한 `useEffect` 도 클릭 같은 상호작용이나 `useLayoutEffect` 에서 발생한 상태 업데이트 등의 상황에서는 Paint 전에 실행될 수 있다. **항상 Paint 이후가 아니라, Paint 전 완료를 보장하지 않는다고 이해한다.** [useEffect 공식 문서](https://react.dev/reference/react/useEffect#caveats)

기본적으로 `useEffect` 를 사용하고, 화면 표시 전에 DOM 측정과 시각적 보정이 꼭 필요한 경우에 `useLayoutEffect` 를 선택한다. 단순히 상태를 화면에 표시하는 작업에는 두 훅 모두 필요하지 않으며, React 가 커밋 단계에서 DOM 에 반영한다.

## 추가 학습: useEffectEvent

`useEffectEvent` 는 Effect 에서 발생한 이벤트를 처리할 때 최신 커밋의 props 와 state 를 읽으면서, 그 값의 변경 때문에 Effect 를 다시 실행하지 않도록 로직을 분리하는 훅이다.

### 연결 조건과 알림에 사용할 값 분리하기

채팅방에서는 `roomId` 가 바뀌면 다시 연결해야 하지만, 알림의 `theme` 만 바뀌었다고 다시 연결할 필요는 없다. 다음 예제의 `createConnection`, `showNotification` 은 앱에서 제공하는 함수라고 가정한다.

```tsx
useEffect(() => {
  const connection = createConnection(roomId);

  connection.on("connected", () => {
    showNotification("연결되었습니다.", theme);
  });

  connection.connect();
  return () => connection.disconnect();
}, [roomId, theme]);
```

이 코드에서는 `theme` 이 바뀌어도 연결을 해제하고 다시 연결한다. 그렇다고 의존성에서 `theme` 만 빼면, 기존 리스너에 등록된 콜백이 이전 렌더의 테마를 참조할 수 있다.

알림 동작을 Effect Event 로 분리한다.

```tsx
const onConnected = useEffectEvent(() => {
  showNotification("연결되었습니다.", theme);
});

useEffect(() => {
  const connection = createConnection(roomId);

  connection.on("connected", () => {
    onConnected();
  });

  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

| 상황 | 동작 |
| --- | --- |
| `roomId` 변경 | 이전 연결을 정리하고 새 방에 연결 |
| `theme` 변경 | 컴포넌트는 재렌더링되지만 연결 Effect 는 재실행하지 않음 |
| 연결 완료 이벤트 발생 | 최신 커밋의 `theme` 으로 알림 표시 |

**테마 변경 자체가 알림을 실행하지는 않는다.** 이후 이벤트가 발생해 `onConnected()` 를 호출할 때 최신 테마를 사용한다. 이미 표시된 알림을 자동으로 변경하는 것도 아니다.

### 이전 테마를 참조하지 않는 이유

일반 콜백은 자신이 만들어진 렌더의 값을 클로저로 참조한다. `theme` 이 `light` 였던 렌더에서 등록한 콜백을 그대로 유지하면, 다음 렌더에서 `theme` 이 `dark` 가 되어도 이전 값을 참조할 수 있다.

`useEffectEvent` 는 React 가 호출 시점에 최신 커밋의 콜백을 실행하도록 관리한다. 다음은 내부 구현 코드가 아닌 동작을 이해하기 위한 흐름이다.

```text
첫 커밋: theme = light → 실행할 콜백 연결
다음 커밋: theme = dark → 최신 콜백으로 갱신
기존 리스너에서 onConnected() 호출 → 최신 값인 dark 사용
```

**기존 클로저 안의 theme 이 바뀌는 것이 아니라, Effect Event 를 통해 최신 콜백이 실행된다.** 리스너를 다시 등록하지 않아도 최신 값을 읽는 이유다. [useEffectEvent 공식 문서](https://react.dev/reference/react/useEffectEvent#parameters)

### 사용할 때 주의할 점

- Effect Event 는 의존성 배열에 넣지 않는다.
- 일반 `onClick` 핸들러로 사용하거나 다른 컴포넌트·훅에 전달하지 않는다. 같은 컴포넌트의 Effect 또는 다른 Effect Event 에서 호출하는 로직에 사용한다.
- 의존성을 숨기는 수단으로 사용하지 않는다. `roomId` 처럼 변경 시 연결을 다시 설정해야 하는 값은 Effect 의 의존성으로 유지한다.
- Effect Event 의 함수 참조가 안정적이라고 가정하지 않는다. 최신 값에 접근하는 기능과 함수 참조의 안정성은 별개다.

[useEffectEvent 공식 문서의 주의사항](https://react.dev/reference/react/useEffectEvent#caveats)

## 추가 학습: useTransition 과 Fiber

### useTransition: 업데이트의 우선순위 구분하기

`useTransition` 은 일부 상태 업데이트를 긴급하지 않은 Transition 으로 표시한다. React 는 그 업데이트의 렌더링 도중 더 급한 업데이트를 먼저 처리할 수 있다. `isPending` 은 Transition 이 진행 중인지 알려준다.

검색창에서는 입력값은 즉시 반영하고, 무거운 결과 화면을 바꾸는 상태는 Transition 으로 처리할 수 있다. 아래 `SearchResults` 는 별도로 정의된 검색 결과 컴포넌트라고 가정한다.

```tsx
import { useState, useTransition } from "react";
import type { ChangeEvent } from "react";

function SearchPage() {
  const [input, setInput] = useState("");
  const [query, setQuery] = useState("");
  const [isPending, startTransition] = useTransition();

  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    const nextValue = event.currentTarget.value;
    setInput(nextValue);

    startTransition(() => {
      setQuery(nextValue);
    });
  }

  return (
    <>
      <input value={input} onChange={handleChange} />
      {isPending && <span>결과 업데이트 중…</span>}
      <SearchResults query={query} />
    </>
  );
}
```

입력창의 `value` 를 제어하는 상태 업데이트는 Transition 으로 처리하지 않는다. 또한 위 구조만으로 긴급 렌더에서 자식의 모든 계산이 생략되는 것은 아니다. 실제 성능은 컴포넌트 구성과 메모이제이션 등을 함께 확인해야 한다.

`startTransition` 의 콜백 자체는 즉시 실행된다. 그 안에서 예약한 상태 업데이트를 Transition 으로 표시하는 것이며, 무거운 JavaScript 계산을 별도 스레드로 옮기거나 요청 횟수를 줄이는 디바운스 기능은 아니다. [useTransition 공식 문서](https://react.dev/reference/react/useTransition)

### Fiber: 렌더링 작업과 진행 상황을 기록하는 구조

FiberNode 는 컴포넌트·요소의 타입, props, state, 업데이트 정보와 다른 Fiber 와의 연결 등을 담는 React 내부 객체다. 실제 DOM 노드와는 다른 구조다.

| 개념 | 역할 |
| --- | --- |
| Fiber | 렌더링 작업을 나누고 진행 상황을 기록하는 구조 |
| Lane | 업데이트의 우선순위와 처리 대상을 구분하는 내부 체계 |
| 스케줄러 | 작업 실행 시점과 제어권 양보를 조율 |
| useTransition | 상태 업데이트를 Transition 으로 표시하는 공개 API |

React 는 작업 단위 사이에서 브라우저에 제어권을 돌려줄 수 있다. 브라우저가 새 입력 이벤트를 처리하면 React 는 긴급한 업데이트를 먼저 처리하고, 남은 렌더를 이어가거나 최신 상태로 다시 계산할 수 있다. 아래는 실제 소스를 단순화한 의사 코드다.

```text
다음 작업이 있는 동안:
  작업 하나 처리
  양보할 때가 되면:
    다음 작업 위치를 유지
    나중에 계속하도록 예약
    실행을 끝내고 브라우저에 제어권 반환
```

단, 실행 중인 컴포넌트 함수 내부의 긴 반복문을 강제로 정지하지는 못한다. React 가 다시 제어권을 얻는 작업 단위 사이에서 양보한다. [React 작업 루프 소스](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberWorkLoop.js)

### current 와 work-in-progress, 렌더와 커밋의 관계

**트리는 UI 와 작업 정보를 담는 구조이고, 페이즈는 그 구조를 처리하는 단계** 다.

| 개념 | 의미 |
| --- | --- |
| current | 현재 커밋된 UI 를 나타내는 Fiber 트리 |
| work-in-progress | 다음 UI 를 계산하기 위해 준비하는 Fiber 트리 |
| 렌더 페이즈 | 다음 UI 를 계산하고 재조정으로 변경 사항 판단 |
| 커밋 페이즈 | 계산한 변경을 실제 DOM 에 반영 |

`count` 가 `0 → 1` 로 바뀌는 흐름은 다음과 같다.

```text
① 업데이트 전
   current: count = 0

② 렌더 페이즈
   current: count = 0 유지
   work-in-progress: count = 1인 UI 계산

③ 커밋 페이즈
   실제 DOM의 숫자를 1로 변경
   완성된 work-in-progress가 새로운 current가 됨
```

렌더 페이즈 동안 기존 current 와 준비 중인 work-in-progress 를 함께 관리한다. 두 트리를 매번 처음부터 통째로 복사하는 것은 아니며, Fiber 객체를 재사용할 수 있다. 실제 DOM 을 두 벌 만드는 것도 아니다.

렌더가 중단되면 준비 중인 작업을 멈추는 것이므로, 이전에 커밋한 화면은 유지된다. 작업이 여전히 유효하면 이어서 처리할 수 있고, 더 최신 업데이트로 불필요해졌다면 이전 렌더를 버릴 수도 있다. 커밋의 DOM 변경을 중간에 끊어 미완성 화면을 보여준다는 의미는 아니다. [React 동시성 설명](https://react.dev/blog/2022/03/29/react-v18#what-is-concurrent-react)

`useLayoutEffect` 는 DOM 반영 이후의 실행 시점을, `useTransition` 은 상태 업데이트로 발생하는 렌더링의 처리 우선순위를 다룬다.

## 추가 학습: use 와 React Query

### use: 렌더링 중 리소스 읽기

`use` 는 렌더링 중 Promise 의 결과나 Context 값을 읽는 React API 다. 일반 훅과 달리 조건문과 반복문 안에서 호출할 수 있지만, 컴포넌트나 훅 안에서 사용해야 한다.

`use(promise)` 는 API 요청 함수 자체가 아니다. 이미 만들어진 Promise 를 받아 그 결과를 읽는다.

```tsx
import { Suspense, use } from "react";

function Message({ messagePromise }: { messagePromise: Promise<string> }) {
  const message = use(messagePromise);
  return <p>{message}</p>;
}

function Page({ messagePromise }: { messagePromise: Promise<string> }) {
  return (
    <Suspense fallback={<p>불러오는 중…</p>}>
      <Message messagePromise={messagePromise} />
    </Suspense>
  );
}
```

위 예제는 서버나 캐시에서 준비한 Promise 를 전달받는다고 가정한다.

| Promise 상태 | 동작 |
| --- | --- |
| 대기 중 | 해당 컴포넌트 렌더링을 보류. 위 예제의 첫 표시에서는 상위 Suspense 의 fallback 표시 |
| 성공 | 결과를 반환하고 해당 데이터로 렌더링 |
| 실패 | 오류를 상위 Error Boundary 로 전달 |

기다리는 동안 JavaScript 실행을 붙잡아 두는 것은 아니다. 결과가 준비되면 React 가 렌더링을 다시 시도한다. 오류 처리를 위해 `use` 를 `try-catch` 로 감싸지 않고 Error Boundary 등을 사용한다. [use 공식 문서](https://react.dev/reference/react/use)

### API 요청을 부모에서 해야 한다는 뜻은 아니다

Promise 를 props 로 전달하는 것은 한 가지 사용 방식이다. 요청 함수나 완료된 데이터가 아니라, 요청 결과를 나타내는 Promise 를 전달한다.

데이터가 필요한 컴포넌트에서 캐시의 Promise 를 읽는 방식도 가능하다. 중요한 것은 클라이언트 렌더링마다 새 Promise 를 만들지 않는 것이다.

```tsx
// 피해야 하는 형태: 렌더링마다 새로운 요청 Promise 생성
const response = use(fetch("/api/message"));
```

캐시, Suspense 를 지원하는 프레임워크 또는 서버 컴포넌트에서 Promise 를 공급한다. 단순히 함수를 컴포넌트 밖으로 옮기는 것만으로 Promise 가 캐싱되지는 않는다. [Promise 캐싱 설명](https://react.dev/reference/react/use#caching-promises-for-client-components)

| Effect 에서 요청하는 방식 | use 로 Promise 를 읽는 방식 |
| --- | --- |
| 커밋 후 Effect 에서 요청 시작 | 서버·캐시 등이 공급하는 Promise 사용 |
| 응답을 state 에 저장 | use 가 Promise 결과를 읽음 |
| 로딩 상태를 직접 분기 | Suspense 로 로딩 UI 처리 |

### React Query 를 쓰고 있다면 필요한가?

API 데이터를 React Query 로 관리하고 있다면 일반적으로 `use` 를 별도로 호출할 필요는 없다. 기존 `useQuery` 로 요청과 상태를 관리하면 된다.

```tsx
const { data, isPending, error } = useQuery({
  queryKey: ["message"],
  queryFn: fetchMessage,
});
```

Suspense 방식이 필요하다면 TanStack Query v5 의 `useSuspenseQuery` 를 사용할 수 있다. 아래 예제의 `fetchMessage` 는 메시지 객체를 반환하는 요청 함수이며, 상위에 QueryClientProvider 가 설정되어 있다고 가정한다.

```tsx
import { Suspense } from "react";
import { useSuspenseQuery } from "@tanstack/react-query";

function Message() {
  const { data } = useSuspenseQuery({
    queryKey: ["message"],
    queryFn: fetchMessage,
  });

  return <p>{data.message}</p>;
}

function MessagePage() {
  return (
    <Suspense fallback={<p>불러오는 중…</p>}>
      <Message />
    </Suspense>
  );
}
```

실제 앱에서는 오류 처리를 위한 Error Boundary 도 구성한다. `useSuspenseQuery` 는 캐시 데이터가 없을 때의 오류를 기본적으로 Error Boundary 에 전달한다. [TanStack Query Suspense 문서](https://tanstack.com/query/latest/docs/framework/react/guides/suspense)

| 도구 | 역할 |
| --- | --- |
| React Query | 서버 데이터의 캐시, 재요청, 무효화 등 관리 |
| React 의 use | 렌더링 중 Promise 결과나 Context 값 읽기 |

`use` 는 React Query 의 대체제가 아니며, 기존 `useQuery` 코드를 바꿔야 하는 이유도 아니다.

## 추가 학습: useSyncExternalStore

`useSyncExternalStore` 는 **React 밖에서 관리되는 값의 변경을 구독해서 화면에 반영하는 훅** 이다. 브라우저 API 나 기존 외부 스토어의 값을 React 컴포넌트와 연결할 때 사용한다.

### 외부 값을 읽기만 하면 변경을 알 수 없다

```tsx
function OnlineStatus() {
  return <p>{navigator.onLine ? "온라인" : "오프라인"}</p>;
}
```

이 코드는 렌더링 시점의 값을 읽지만, 브라우저의 온라인 상태가 바뀌었다는 이유만으로 다시 렌더링되지는 않는다. React 에 변경을 알려줄 구독이 필요하다.

### 현재 값 읽기와 변경 구독하기

| 인자 | 역할 |
| --- | --- |
| `subscribe` | 변경 알림을 받을 콜백을 등록하고, 구독 해제 함수를 반환 |
| `getSnapshot` | 컴포넌트에서 사용할 현재 값을 반환 |
| `getServerSnapshot` | 서버 렌더링과 초기 hydration 에서 사용할 값을 반환하는 선택적 인자 |

```tsx
import { useSyncExternalStore } from "react";

function getSnapshot() {
  return navigator.onLine;
}

function subscribe(onStoreChange: () => void) {
  window.addEventListener("online", onStoreChange);
  window.addEventListener("offline", onStoreChange);

  return () => {
    window.removeEventListener("online", onStoreChange);
    window.removeEventListener("offline", onStoreChange);
  };
}

// 브라우저에서만 렌더링하는 예제
function OnlineStatus() {
  const isOnline = useSyncExternalStore(subscribe, getSnapshot);

  return <p>{isOnline ? "온라인" : "오프라인"}</p>;
}
```

```text
브라우저의 온라인 상태 변경
  → online / offline 이벤트 발생
  → 등록한 onStoreChange 호출
  → React 가 getSnapshot() 으로 현재 값 확인
  → 이전 값과 다르면 재렌더링
```

변경 알림 콜백은 새 값을 직접 전달하는 대신, React 가 값을 다시 읽도록 알린다. React 는 스냅샷을 `Object.is` 로 비교한다. `subscribe` 를 컴포넌트 밖에 선언하면 매 렌더링마다 새 함수가 전달되어 불필요하게 재구독하는 것을 피할 수 있다.

### 서버 렌더링과 스냅샷 주의사항

서버 렌더링에서도 이 컴포넌트를 사용하려면 `getServerSnapshot` 을 제공해야 한다. 서버에서 반환한 값과 클라이언트의 초기 hydration 에서 반환한 값이 일치해야 한다. 위 예제는 브라우저 전용이므로 생략했다.

객체나 배열을 스냅샷으로 반환한다면 **데이터가 바뀌지 않았을 때는 같은 참조를 반환**해야 한다. 매번 새 객체를 만들면 변경된 값으로 판단되어 반복 렌더링 문제가 생길 수 있다. 데이터가 바뀌면 새 불변 스냅샷을 반환한다.

일반적인 컴포넌트 상태는 `useState` 나 `useReducer` 로 관리하면 된다. `useSyncExternalStore` 는 React 가 직접 관리하지 않는 상태를 연결할 때 사용한다. [useSyncExternalStore 공식 문서](https://react.dev/reference/react/useSyncExternalStore)
